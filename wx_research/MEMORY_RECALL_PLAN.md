## 零、v1 的错误与更正（保留，说明什么证据会改变判断）

v1 曾经标"方案已定"，那是错的。经 YG 复核，以下三处必须更正：

### 错误 1：LOCOMO / Mem0 基准表 —— 引用了一个编造数据的二手中文博客

v1 写的是：

> 全量上下文注入 72.9% / 10–17 秒；选择性检索（图记忆）**89.9%** / **<2.6 秒** /
> token 降 90%（来源：mumega.com 博客）

**原始论文（arXiv 2504.19413v1《Mem0》Table 2）的真实数据**：

| 方法 | Tokens | search p50 | search p95 | total p50 | total p95 | J（LLM-as-Judge） |
|---|---:|---:|---:|---:|---:|---:|
| **Full-context** | 26031 | – | – | 9.870 | **17.117** | **72.90 ± 0.19%** |
| A-Mem | 2520 | 0.668 | 1.485 | 1.410 | 4.374 | 48.38 ± 0.15% |
| LangMem | 127 | 17.99 | 59.82 | 18.53 | 60.40 | 58.10 ± 0.21% |
| Zep | 3911 | 0.513 | 0.778 | 1.292 | 2.926 | 65.99 ± 0.16% |
| OpenAI | 4437 | – | – | 0.466 | 0.889 | 52.90 ± 0.14% |
| **Mem0** | 1764 | 0.148 | 0.200 | 0.708 | **1.440** | 66.88 ± 0.15% |
| **Mem0^g** | 3616 | 0.476 | 0.657 | 1.091 | **2.590** | **68.44 ± 0.17%** |

事实与 v1 相反：

- **全量上下文（72.90%）准确率最高**，Mem0 / Mem0^g 分别低 6.02 / 4.46 个百分点。
- 「89.9%」在论文中不存在；「准确率提升 17 点」实际是**下降约 4.5 点**。
- 论文摘要的准确表述是「**91% lower p95 latency**、**>90% token saving**」——
  这是**用准确率换延迟和成本**的取舍，不是全面胜出。

**结论变更**：LOCOMO 不能用来论证"应该做检索"。恰恰相反，**在绯栀这种
1892 字符的小体量下，全量注入在准确率上反而更安全**（且延迟代价可以忽略，
因为 full-context 的 17 秒来自 26031 token 的 LOCOMO 对话，不是 1892 字符的记忆）。

### 错误 2：否定 agent 的理由站不住

| v1 的说法 | 问题 |
|---|---|
| 「给她 bash/文件系统，人设就死了」 | agent ≠ bash。可以只暴露 `recall_memory` 等少量只读工具。这是修辞不是论证。 |
| 「已读不回与 agent 有结构性冲突」 | 没有依据。是否回复是明确的行为选择，与是否存在工具循环无关。角色感取决于目标/提示/状态/输出控制。 |
| 「工具结果变化 → 稳定前缀缓存全面失效」 | 过度绝对。DeepSeek 官方说明共同前缀可识别、持久化、复用；实际影响取决于工具消息插入位置与缓存单元时机。 |
| 「总延迟轻松超过 60 秒」 | 算术不成立。25 + 9 + 3×5 = **49 秒**，且这些是上界。必须测端到端 p50/p95，不能拿上界相加当结论。 |
| 「两个 QQ 项目都没有让主对话模型跑 tool loop」 | **事实错误**。`dsh-im-qq` README 第 5 行即写明"直接与 harness 的**完整 agent** 对话"，架构图中含 `agent.followup(...)`。 |

**修正后的立场**：暂不引入通用 agent，**理由是尚未证明增加自主调用能带来收益**，
而不是"agent 天生不适合陪伴角色"。后者是未经验证的价值判断。

### 错误 3：排除向量检索的规模论证不成立

v1 说"她的记忆是中文短句、同一种口吻，语义鸿沟接近零"。**这条没有依据**——
记忆是模型写的，不代表用户查询会用相同词语。反例：

> 记忆：「他不喜欢吃香菜。」
> 当前消息：「点外卖有什么要忌口的？」

词面匹配完全失效。所以"96 条所以不需要向量"是错的。

另外 v1 把**三个独立选择混成一个**：是否用 embedding / 是否用向量数据库 /
是否调远程服务。**本地 embedding 不需要数据库也不需要远程服务。**

还有一个逻辑漏洞：v1 的触发条件是"记忆 > 300 条"，但代码上限是
`MAX_FACTS=60 + MAX_EVENTS=40 = 100` —— **那个分支永远不可能触发**。

> v1 曾把 1270 当"全部记忆体积"，**口径错误**。1892 才是全长，1270 是截断后的渲染结果。

### 2.2 数据质量

- **高相似对 15 对（Jaccard ≥ 0.45）**。注意：**这不等于 30 条独立冗余**，
  同一条可能参与多对；Jaccard 只能筛候选，无法区分"喜欢/不喜欢"、
  "事实补充"与"真正重复"。此数字需人工标注后才可作真值。
- 典型重复形态：同一事在 facts 与 events 各存一份
  （`绯栀描线稿手腕酸…` vs `绯栀跟<OWNER>讲了她描线稿手腕酸…`）。
- facts 中疑似一次性流水账 19/56（如"<OWNER>中午吃的是辣椒炒肉"）——
  **同样是启发式判定，需人工确认**。

### 2.3 记录结构缺陷（已核实）

```
facts[0]  = {"text": "<OWNER>明天9点有课", "added": "2026-10-16"}
events[0] = {"text": "绯栀给<OWNER>拍了糊糊四脚朝天…", "added": "2026-10-18"}

有 id 字段      :  0 / 96
有 source 字段  :  0 / 96
有 added 日期   : 96 / 96
```

**没有独立记忆 ID、没有来源、没有事实发生时间。**

> **性质区分（避免把缺陷当成已发生的错误）**：
> 这是**结构缺陷**——它使 CRUD、追溯与纠错**做不到**，也阻碍验证；
> 但它**本身不能证明现有的追加式抽取已经产生了错误**。
> 「已观察到的错误」目前只有一处有证据：重复入库（§2.2 的 facts/events 双份）。
> 三者要分开记：**缺陷 / 失效风险 / 已观察到的错误**。

## 三、抽取质量缺陷（按实测分级，不一律叫 P0）

### 3.1 全局窗口可能漏抽 —— **潜在风险，当前未触发**（降级为 P1）

```python
# store.py
def recent(self, limit=10):
    SELECT id, peer_wxid, role, text, sent_at_ms, source FROM messages
    ORDER BY id DESC LIMIT ?          # ← 全局，不按 peer 过滤

# memory.py maybe_extract()
rows = store.recent(limit=120)                     # 全局最新 120 条
fresh = [r for r in rows if r.peer_wxid == peer and r.id > last_id]
batch = fresh[:60]
self.data["last_id"] = max(r.id for r in batch)    # 水位推进
```

**理论失效路径**：若两次抽取之间窗口被其他会话挤占、或积压超过 120 条，
更早的 `id > last_id` 消息不在候选集里，而水位仍推进 → 那些消息永久不被抽取。

**实测（2026-10-25）**：

```
messages 总量 516 条，id 1..519
最近 120 条里目标会话占 119 条，其他会话仅 1 条
last_id = 510，水位之后待处理 9 条
```

**结论（限定表述）**：**当前快照未发现窗口溢出**；但这**不能证明历史上从未漏抽**——
停机、调用失败、抽取节流期间的积压都可能造成过，尚未核对。
而且**单会话积压同样能触发**（不需要等到加群聊或多白名单）：
只要两次成功抽取之间该会话自己超过 120 条，窗口就装不下。

**仍建议修**（成本低、是隐患）：按 `(peer_wxid, id > last_id)` 在 SQL 层分页即可。

> 顺带发现一条脏数据：`messages` 里有 1 条 `peer_wxid = "wxid99r5idk4n8or22"`
> （**缺 `wxid_` 后的下划线**），与正常的 `<WXID_FRIEND_A>` 不是同一 key。
> 目前**只能确定它与正常 key 不同**。应先追溯原始入站数据与写入路径，再决定是否修复；
> **不要仅凭格式相似就自动合并身份**。

### 3.2 抽取输入缺少时间戳 —— **当前即影响**（P0）

`EXTRACT_SYSTEM` 要求「不要写今天/明天，要落成具体日期」，但构造输入时：

```python
convo = "\n".join("%s：%s" % (角色, text[:800]) for r in batch)
```

**没有传 `sent_at_ms`**（数据库里有这一列）。模型只能猜日期或省略时间，
「昨天/明天 → 具体日期」的转换因此不可靠。这一条与数据量无关，**现在就在发生**。

### 3.3 抽取时看不到已有记忆 —— **当前即影响**（P0）

```python
known = "\n".join("- " + x["text"] for x in self.facts()[-30:])   # 只有 30 条 facts
```

- 看不到全部 56 条 facts
- **看不到任何 events**（而 events 已满 40 条）

所以即使提示词要求"不要重复"，模型也缺少判断依据。这比"只能 append"更具体，
也是重复入库的直接成因。**现在就在发生。**

## 四、调研结论

### 4.1 两个 QQ 项目，两种范式

**`dsh-im-qq`** = **完整 agent 路线**：接入 harness 完整 agent（工具 / 记忆 /
子代理 / 文件系统 / 审批桥 / 工作区隔离），架构中 `agent.followup(...)`
把 IM 消息喂进 agent 会话。**它确实跑了 tool loop。**

**`Xiaoke-qqbot`** = **编排式路线**：判断交给独立服务（JEV），记忆交给网关做
召回/记录，主模型负责单轮生成。自述边界："一条回复可能包含**多次模型请求**"、
"阈值/概率/冷却/预算共同影响触发"、"把对话模型切到 DeepSeek 不会自动获得联网能力"。

**结论**：两种都存在，差别是"谁来决策、需要几轮、代价多少"，**不存在
"agent 不适合 IM"的规律**。

### 4.2 DeepSeek 实际能力（官方文档核实）

- 模型：`deepseek-flash`、`deepseek-v4-pro`
- **没有 embeddings 端点**（API 仅 chat / responses / files / search / fetch）
- `thinking.type: enabled|disabled`、`reasoning_effort: none|low|high|max`
- `tools` + `strict` + `tool_choice` 可用
- 前缀缓存：共同前缀可识别并复用（KV Cache 文档）

## 五、技术路线：三个待验证的假设（不再预设结论）

| 假设 | 验证方式 | 若成立 | 若不成立 |
|---|---|---|---|
| H1：词面匹配在真实查询上够用 | 固定查询集，人工标注召回 | 不上 embedding | 上本地 embedding |
| H2：全量注入 + 重排序优于筛选 | 同批查询对比回答正确率 | 保留全量 | 引入 top-k |
| H3：增加一轮自主调用有净收益 | 端到端 p50/p95 + 回答质量 | 做受限工具调用 | 保持单轮 |

**注意 H2**：Mem0 论文比较的是「**完整原始对话**」vs「**抽取压缩后的记忆系统**」，
而这里要比较的是「**全部已抽取记忆**」vs「**其中一部分**」。两者之间隔着抽取损失、
模型、提示词和任务差异，**不能直接类比**。

所以正确表述是：

> **全量注入作为小规模系统的「优先基线（first baseline）」**，
> 依据是**实现简单、避免筛选造成的信息遗漏、当前规模允许尝试**。
> 「准确率更安全」「延迟代价可忽略」都保留为**待测判断**。

另外 **重排序本身是一个独立假设**：全量注入有效，不蕴含重排序会改善结果。
二者必须分开验证（见第 0 步的四组对照）。

> 口径提醒：1892 是**纯文本字符数**，既不是渲染长度、也不是 token 数。
> 生产模板下：截断渲染 1270、全量 2337；统一评测模板下：截断 1237、全量 2579
> （模板不同，两套数字不可直接比）。**token 数至今未实测。**

   它只能说明"单独缩减记忆段能省多少输入"，**不能约束"对回答质量影响多大"**。

**尚未回答**：五组（含 `none`）的**回答质量差异**、重排序是否有效、抽取阶段丢了多少、
历史通道能否补齐、holdout。
**因此：证据在 ≠ 回答对，本步不能得出任何路线结论。**

### 第 0.5 步 · 补第二套任务用例（抽取质量）—— 必做

第 0 步只测了「使用固定记忆回答查询」。**另一半任务是「从原始对话抽取记忆」**，
只测前者发现不了抽取阶段已经丢失的信息。

做法：从 `messages` 里挑若干段对话（含被纠正、被更新、含相对时间的片段），
标注「这段里应该抽出哪些记忆 / 不该抽出什么」，作为抽取质量的判据。

**没有它，第 1 步改完无法判断是变好还是变坏。**

### 第 1 步 · 修抽取质量与写入安全（按 §3 实测优先级）

先做**当前就在影响**的两条：

1. **抽取输入补时间戳**（§3.2）：把 `sent_at_ms` 按本地时间格式化进 `convo`
2. **抽取时给完整已有记忆**（§3.3）：facts 全量 + events 全量，而非 `facts[-30:]`

再做写入安全：

3. 引入稳定记忆 ID（并迁移现有 96 条）
4. 记录**来源消息 ID + 陈述类型**（用户明确陈述 / 角色自述 / 模型推断）与事实发生时间。
   **只有类型没有出处无法追溯**；旧记忆无法可靠对应原消息时标「来源未知」，
   **迁移时不得补造出处**。
5. 支持类型迁移（facts ↔ events）
6. 操作校验：验证 ID、字段、版本；**删除先归档**，不物理删除

最后修隐患：

7. 按 `(peer, id > last_id)` 在 SQL 层分页，替换全局 120 窗口（§3.1，当前未触发）

### 第 2 步 · 比较渲染方案（同一份**未清洗**数据上先做）

v2 初稿的三组同时改变了「可见范围 + 顺序 + 内容」，无法归因。改成四组，
**先固定数据不变，只动渲染**：

1. `truncate` —— 当前截断方式
2. `full_orig` —— 全量、原顺序
3. `full_rerank` —— 全量、重排序
4. `topk8` —— **同一排序方法下**取 top-k

这样：2 对 3 单独检验"重排序"；3 对 4 单独检验"筛选"；1 对 2 单独检验"可见范围"。

**之后再**比较清洗前后（去重 + 类型迁移），才能知道收益来自哪里。
两阶段不能混着做。

holdout 集（3 条）**调参期间不看**，只在方案定稿时跑一次，避免用同一批题
边调边证明自己有效。

### 第 3 步 · 模型路由 vs 规则（H3）

把"要不要搜 / 要不要接话 / 要不要发语音"做成一次极小的结构化调用
（`deepseek-flash` + `thinking:disabled`，≤200 token），与现有关键词/概率启发式对比。

> **命名要精确**：这一步测的是「**模型路由是否优于现有规则**」，
> **不等于**测「主对话模型自主调用工具（tool loop）的收益」。
> 两者可以分别做实验，但结论不能互相借用。

### 第 4 步 · 最后设计遗忘

- 先做**降权/归档**，不做物理删除
- 区分三种状态：**未被展示**、**被展示但未被使用**、**被实际引用**
- 不能用 `hits=0` 直接判死 —— 会形成"召回不到→没有命中→更容易被删"的反馈循环

## 八、验收指标（修订版，防"数字变好、信息变少"）

| 维度 | 指标 | 说明 |
|---|---|---|
| 信息保留 | 查询集上的**漏召回率** | 主指标。不能用"条数变少"当成果 |
| 回答正确性 | 模型裁判或人工判定的正确率 | 与基线对比，不是绝对值 |
| 延迟 | 端到端 p50 / p95 | 必须实测，不用上界相加 |
| 成本 | prompt token + 总调用成本 | **允许上升**，若换来正确率提升 |
| 重复 | 人工标注后的真实重复数 | 不再用 Jaccard 对数当结论 |
| 完整性 | 抽取覆盖率：库内消息是否都被抽过 | 防止 3.1 的漏抽 |

**删除 v1 的三条错误指标**：
- ~~"60±10 条"~~ —— 分类迁移不减信息量，条数不是目标
- ~~"prompt token 不上升"~~ —— 与"让此前不可见的记忆重新可用"直接冲突
- ~~"20 个查询 85%"~~ —— 只够冒烟，不足以说明稳定性

## 十一、一句话结论（v2.1）

> **v1 的核心错误是拿一份编造数据的二手博客当决策依据，把"用准确率换延迟"
> 误读成"检索全面胜出"。** 更正后：Mem0 论文比的是「完整原始对话 vs 抽取压缩后的
> 记忆」，与这里「全部记忆 vs 其中一部分」不可类比 —— 所以全量注入只是
> **优先基线**（实现简单、避免筛选遗漏、规模允许尝试），不是已被证明的更优解。
>
> **当前即影响抽取质量的是两条**：输入没带消息时间戳（"昨天/明天"落不成具体日期）、
> 抽取时看不到任何 events（只有 `facts[-30:]`），后者是重复入库的直接成因。
> 全局窗口漏抽是**尚未触发的隐患**，单会话积压同样能触发，仍应修但不必前置。
>
> **第 0 步已给出基线（v3），但它只覆盖「记忆通道」一种口径**：
> `none` 0/11、`truncate` 11/11、`full_*` 11/11、`topk8` 7/11（按答案要点逐条）。
> 历史通道目前**只做了关键词粗筛，未参与完整率**，所以「截断正在造成损失」
> 与「必须全量」两边都**没有被证明**，也都没有被否定。
>
> **下一步唯一有意义的事是跑回答质量对照**，且必须包含 `none` 组
> （无长期记忆、其余输入不变）。
>
> **预设的结论边界**（先写下，防止事后过度解读）：
> 若各组的答案质量接近，第一轮能得出的全部结论只是——
> **「在当前快照、这批查询、指定模型及完整历史输入条件下，
> 未观察到长期记忆带来的明显回答质量提升」**。
> 14 条样例、每题一次生成，**即使分数相同也不足以证明两组等效**，
> 更不能外推到历史被压缩之后的阶段。
>
> 在那之前，全量 / 筛选 / 向量三条路线都保持候选状态。
