# 绯栀的长期记忆 —— 设计与实现（2026-10-16）

## 问题

用户反馈「这个 ai 的记忆非常有限」。查代码发现两个叠加的原因：

1. **上下文只有 8 条**（`autoreply.py` 里 `store.history(peer, limit=8)`）—— 约等于 4 轮对话，
   更早的内容对她**等于不存在**。
2. **整套系统没有任何长期记忆机制** —— 没有摘要、没有事实抽取、没有检索。

而 `persona.py` 里却写着她

> 「你**记得小事**。他随口说过的话你都记着，因为从小被忽略的人对「被记住」特别在意」

**人格承诺了一套技术上做不到的能力** —— 于是表现成"记性很差、每轮都像重新认识"。

## 方案：三层记忆

| 层 | 内容 | 实现 |
| --- | --- | --- |
| 工作记忆 | 最近 24 条原始消息 | `autoreply` 里把 `limit` 从 8 提到 24 |
| 事实记忆 | 关于<OWNER>的稳定信息（工作/学业/作息/喜好/约定） | 模型抽取，存 `state/feizhi_memory.json` |
| 情节记忆 | 最近发生的事（一句话 + 日期） | 同上 |

事实与情节由模型从新对话里抽取，每轮渲染成一段注入 system prompt。

## 实现

新增 `feizhi_pc/memory.py`（无第三方依赖）：

- `FeizhiMemory.render()` —— 渲染成注入用的一段，并附**使用说明**
  （"像真人一样自然想起来就用，别一次全倒出来，也别复述成清单"）
- `FeizhiMemory.maybe_extract(store, peer, llm)` —— 抽取，自带节流：
  **至少 8 条新消息 + 距上次 ≥20 分钟**才真跑一次 LLM，避免每次都多花一次调用
- 去重按文本归一化（前 16 字），容量上限 facts 60 / events 40（超出丢最旧的）
- 全程 try/except 包裹：记忆出错绝不能影响回复

`autoreply.py` 的改动：

1. `FeizhiReplyGenerator` 加 `memory_ctx` 字段，在 `_build_system` 里插到**真实对话之前**
   （位置：人格块之后、联网检索结果之前 —— 记忆是"底"，检索是"当场的补充"）
2. `AutoReplier.__init__` 建 `FeizhiMemory()` 并打日志（便于确认载入）
3. 生成前 `self.gen.memory_ctx = self.memory.render()`
4. 生成成功后**后台线程**触发抽取（不阻塞收消息）

## 验证

用真实历史（200 条）抽取出 7 条事实 + 3 条情节，均为真实对话内容：

```
关于<OWNER>：
- <OWNER>要参加国家级职业生涯规划大赛（A3），本周末20点前交
- <OWNER>在石家庄 / 明天9点有课
- 绯栀养了一只叫糊糊的宠物，会啃她的画笔
```

带上记忆后跑三个探针（本地生成，不发微信）：

| 提问 | 回复要点 |
| --- | --- |
| 你还记得我要参加什么比赛吗 | "国家职业生涯规划比赛（A3）那个，本周末20点前交" + 追问写完没 |
| 我明天有什么安排来着 | "你不是9点有课吧" + 接着催比赛进度 |
| 你那只猫最近干嘛了 | "糊糊啊…趴我一边尾巴扫来扫去，还踩了一脚画板" |

说明模型确实在用记忆，而不是碰巧答对。

## 已知边界与可调项

- **相对时间**：抽取 prompt 已要求"不要写今天/明天/昨天，要落成具体日期或省略"，
  但第一版仍有"<OWNER>明天9点有课"这类条目 —— 会随时间失效，后续可加定期重写。
- **没有检索**：目前是全量渲染（facts 最多 30 条 + events 最近 12 条进 prompt）。
  条目多起来之后需要按当前话题检索，否则会挤占上下文。
- **抽取成本**：每次抽取 = 多一次 LLM 调用，已用节流压到"20 分钟 + 8 条新消息"。
- **`last_id` 水位**：记录已抽取到的消息 id，只抽增量；重置它会把历史重新抽一遍。

## 全量上下文 + 超限压缩（2026-10-17 晚，用户提出的架构调整）

用户反馈：「不应该设置固定的上下文，我想的是直接像你的会话一样，上限直接压缩，这才能成为一个真人」。

同意 —— 固定条数（无论 8 / 24 / 40）本质是"她只记得最近 N 句"，而真人是**全都记得、
太久远的自然变成模糊印象**。所以改成压缩而不是截断。

### 实现（`feizhi_pc/history.py`）

1. **不设固定条数**：全量历史按 id 正序全部进 prompt
2. **超预算才压缩**：`CHAR_BUDGET = 20000` 字符（中文约 1.5~2 token/字，≈30~40k token，
   DeepSeek 上下文 64k，给 system prompt 和输出留足余量）
3. **压缩方式**：把较早的 65% 交给模型压成一段**她自己视角的回忆**（第一人称叙述，
   不分点罗列），保留最近 35% 原文
4. **摘要累积**：`旧摘要 + 新一批消息 -> 新摘要`，`covered_until_id` 记录覆盖到哪条消息，
   下次只处理更新的部分
5. **失败不丢**：压缩调用失败就原样返回长上下文，宁可长一点也不能丢

### prompt 结构（自下而上）

```
system = 人格/格式约束 + 事实记忆（facts/events）+ 全量上下文 + 联网检索结果
context = 【她记得的更早的事（自己的回忆）】 + 【最近的对话（原文）】
```

事实记忆和对话历史分工：前者是"记得关于你的事"，后者是"记得我们聊过什么"。

### 实测

- 库内 245 条消息 → **全部进上下文**，总字符 4244（远低于预算，不触发压缩）
- system prompt 12349 字符（≈8~10k token）
- 按当前字数密度，要涨到 **约 1100 条消息**才会第一次压缩

### 与旧实现的对比

| 版本 | 实际喂进模型的量 |
| --- | --- |
| 最初 | 8 条（`store.history(limit=8)`） |
| 第一次改 | 24 条 —— 被 `select_history(limit=12)` 砍回 9 条 |
| 第二次改 | 40 条（直接切片） |
| **现在** | **全部（245 条），超 20000 字符才压缩** |

## 事故与修复（2026-10-17）



### 事故 1：JSON 碎片被当成回复发出去

微信聊天里出现这些：

```
{"messages":[{"text":"哦...
...
","think_before_ms":520,"typing_ms":680,"delay_after_ms":380},{"text":"我刚没反应过来
```

**根因**：模型输出被截断（`max_tokens=560`）→ `json.loads` 失败 →
Hermes 的 `_parse_plan` 兜底 `cls._fallback_plan(_clean_reply(raw) or raw)`
**把整段 JSON 当文本**，再被切成几段发出去。

更糟的是这些碎片进了数据库，下一轮又作为"她说过的话"回到上下文 —— **会自我强化**。

**修复**：`FeizhiReplyGenerator._call_api` 返回前加 `_sanitize_output()`：

1. 合法 JSON → 原样返回
2. 残缺 JSON → 正则把 `"text":"..."` 抠出来，重组成合法 JSON
3. 纯文本（无 JSON 痕迹）→ 包装成一条消息
4. 都不行 → 一句自然兜底（"…我刚走神了一下，你再说一遍"），**绝不发 JSON 残渣**

**数据清理**：库里 2 条碎片（id 242 / 245）已替换为占位文本。

### 事故 2：上下文实际只有 9 条

`autoreply` 传 24 条，但 Hermes 的 `select_history(limit=12)` 语义是
「最近 6 条 + 关键词匹配 ±1」，`limit` 只是**上限**不是"取多少" ——
实测输入 80 条、筛选后只剩 9 条。

**修复**：`FeizhiReplyGenerator.generate_plan` 不再调 `select_history`，
直接 `history[-40:]`；`autoreply` 取数放宽到 80 条。实测 context 从 268 → 911 字符。

### 附带发现

`autoreply.py` 顶部**没有 `import re`**（只在个别函数里 `import re as _re`），
新加的 `_sanitize_output` 一运行就 NameError —— 已补 `import re`。

### 教训

- **兜底逻辑比主逻辑更危险**：主逻辑失败时用户看不到，兜底失败时会直接把垃圾发出去
- **数据库会放大 bug**：错误的输出进入历史后会被反复喂回模型
- 两处"调大参数"（8→24、12→40）都被上游的隐式截断吃掉，改参数前必须确认整条链路的实际生效值
